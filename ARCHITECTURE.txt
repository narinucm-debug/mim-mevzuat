2. NEDEN BU KATMANLAMA
----------------------------------------------------------------
Citation Enforcer, Answer Composer'dan AYRI ve ondan ÖNCE gelen bağımsız
bir kod katmanı olarak tasarlanmalı. Sebep: "LLM'e prompt ile kaynaksız
cevap verme" demek yeterli güvenlik değildir — modelin prompt'u ihlal
etmesi (hallucination) her zaman mümkündür. Bu yüzden:

  - Retrieval sonucu BOŞSA -> Answer Composer hiç çağrılmaz, sabit
    "yeterli dayanak bulunamadı" mesajı döner.
  - Cevap üretildikten SONRA, cevaptaki her atıf (madde no, belge adı,
    URL) mekanik olarak retrieved-context içinde var mı diye kontrol
    edilir (post-hoc citation validation). Eşleşmeyen atıf varsa cevap
    kullanıcıya gösterilmeden reddedilir/düzeltilir.

Bu iki kontrol (pre-generation gate + post-generation validation)
projenin en kritik güvenlik bileşenidir; TEST_STRATEGY.txt'deki
hallucination testleri doğrudan bunları hedefler.

3. ÖNERİLEN TEKNOLOJİ YIĞINI (Faz 1)
----------------------------------------------------------------
Gerekçe: local-first, tek geliştirici/küçük ekip, hızlı iterasyon,
Türkçe metin işleme ve PDF/OCR ekosisteminin olgunluğu.

  Backend dili:      Python 3.11+
                      (PDF/OCR/NLP kütüphane olgunluğu; FastAPI ile
                      hızlı API; Node/TS alternatif olarak da uygundur,
                      ama Python'ın metin-ağırlıklı ingestion işleri
                      için ekosistemi daha güçlü)
  API çatısı:        FastAPI
  Yapısal veri:      SQLite (Faz 1) -> Postgres'e taşınabilir (Faz 3+,
                      çok kullanıcı/cloud ihtiyacı doğarsa)
  Tam metin arama:   SQLite FTS5 (BM25) — ek servis kurulumu gerektirmez
  Vektör arama:      sqlite-vec veya LanceDB (yerel, embedded, dosya
                      tabanlı — ayrı bir vektör DB sunucusu gerekmez)
  Embedding modeli:  Çok dilli, Türkçe destekli açık model
                      (ör. BAAI/bge-m3 veya intfloat/multilingual-e5) —
                      yerel çalıştırılabilir, veri dışarı çıkmaz
  PDF çıkarımı:      PyMuPDF (fitz) / pdfplumber — native text layer;
                      OCR yalnızca taranmış belgeler için (Tesseract
                      veya benzeri), varsayılan olarak KAPALI
  LLM erişimi:        Sağlayıcı-agnostik arayüz (bkz. bölüm 6)
  UI (Faz 1):        Basit yerel web arayüzü (FastAPI + sunucu-render
                      şablon veya hafif bir SPA) — native masaüstü/mobil
                      YOK. Amaç: çekirdeği kanıtlamak, UI'ye yatırım
                      sonraki fazda.
  Sürüm kontrol:     Git (yerel repo, bu turda başlatıldı)

Bu yığın kasıtlı olarak "ağır" değildir. Kubernetes, mikroservis,
mesaj kuyruğu vb. bu ölçekte GEREKSİZDİR ve eklenmemelidir.

4. PLATFORM STRATEJİSİ
----------------------------------------------------------------
Hedef nihai: Windows, macOS, iOS/iPadOS, Android, Web.
Faz 1 kararı: yalnızca yerel web arayüzü (tarayıcıda çalışan, tek
makinede barındırılan). Gerekçe:
  - Çekirdek (ingestion/search/RAG/citation/rule engine/project
    context) platform bağımsızdır; UI katmanı buna göre kolayca
    genişletilebilir.
  - Cross-platform native UI yatırımı, çekirdek doğrulanmadan yapılırsa
    israf riski taşır (kullanıcının kendi ilkesiyle uyumlu: "Kod miktarı
    başarı metriği değildir").
  - Web arayüzü aynı zamanda gelecekte masaüstü (Electron/Tauri) veya
    mobil (aynı API'yi tüketen native uygulama) için doğrudan temel
    oluşturur.

5. LOCAL-FIRST vs CLOUD
----------------------------------------------------------------
  Yerel tutulacaklar:
    - Mevzuat corpus'u (ham + parse edilmiş metin)
    - FTS5 index
    - Embedding index
    - Proje verileri (Project Mode)
    - Kullanıcı yüklediği belgeler

  Ağ/bulut gerektiren:
    - LLM çağrıları (sağlayıcıya göre değişir; yerel model seçilirse
      bu bile opsiyonel hale gelir — bkz. bölüm 6)
    - Güncel mevzuat kontrolü (Update Engine'in resmi siteleri taraması)

  Bu ayrım şu faydayı sağlar: kullanıcı offline modda bile ZATEN
  INGEST EDİLMİŞ mevzuat üzerinde arama/hesap yapabilir; yalnızca
  "güncel mi?" kontrolü ve LLM'in doğal dil üretimi ağ ister.

----------------------------------------------------------------
6. LLM PROVIDER ABSTRACTION
----------------------------------------------------------------
Tek bir sağlayıcıya kilitlenmeme zorunlu tasarım kuralı. Arayüz:

  interface LlmProvider:
      understand_query(nl_query, context) -> StructuredQuery
      compose_answer(structured_query, retrieved_evidence) -> DraftAnswer
      # NOT: compose_answer yalnızca retrieved_evidence içeriğini
      # kullanabilir; kendi "bilgisini" enjekte edemez (bu kural
      # prompt seviyesinde VE post-hoc validation ile zorlanır)

  Sağlayıcı implementasyonları: Claude, OpenAI, Gemini, Ollama/local.
  Faz 1: tek sağlayıcı (öneri: Claude, çünkü uzun bağlam + citation
  takibi güçlü) ile başla, ama arayüzü genel tut. Sağlayıcı değişimi
  konfigürasyon değişikliği olmalı, kod değişikliği olmamalı.

  LLM'in sistemdeki rolü KESİNLİKLE şunlarla sınırlı:
    - query understanding (doğal dil sorusunu yapılandırılmış filtreye
      çevirme: jurisdiction, topic, sayısal parametreler)
    - retrieval orkestrasyon (hangi ek aramalar gerekebilir)
    - retrieved evidence üzerinde reasoning
    - doğal dil cevap formatlama
  LLM bir mevzuat veritabanı DEĞİLDİR ve öyle kullanılmayacaktır.
